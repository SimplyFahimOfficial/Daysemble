# Security and privacy practices

How Daysemble is built and released securely, what CI enforces, and which exceptions were reviewed.
To report a vulnerability, see the [security policy](../SECURITY.md).

## The app

| Area | State | Enforced by |
| --- | --- | --- |
| Network | HTTPS only: `cleartextTrafficPermitted="false"`, system CAs only (no user-installed CAs) | `res/xml/network_security_config.xml`; APK audit |
| Endpoints | Only Google APIs (`www.googleapis.com/calendar/v3`, `tasks.googleapis.com/tasks/v1`) and Google sign-in, and only after the user connects an account | code review |
| Tokens | OAuth access tokens are held in memory only and never written to disk or logs. The account store keeps the account email and two on/off switches | `data/google/auth/AccountStore.kt` |
| Backups | Enabled, limited to the settings DataStore (`settings.preferences_pb`) by `backup_rules.xml` and `data_extraction_rules.xml`. Database, outbox and account state are not backed up | APK audit (rules must be present) |
| Exported components | `MainActivity`, the reminder receivers and the androidx startup provider are not exported. Exported: the 3 launcher aliases, and library components protected by a permission (WorkManager `SystemJobService` and `DiagnosticsReceiver`, `ProfileInstallReceiver`, Play services `RevocationBoundService`) | APK audit; lint `Exported*` as errors |
| PendingIntents | All `FLAG_IMMUTABLE` | lint `UnspecifiedImmutableFlag`, `MutableImplicitPendingIntent` as errors |
| Logging | One log line in release code, with an exception class name only. No event, task or account content | code review |
| Database queries | Room with bound parameters; `LIKE` patterns are escaped | code review |
| Release build | R8 minification, not debuggable, signed with APK Signature Scheme v2/v3 | APK audit; release workflow |
| Android 15+ | Native libraries (from androidx) are 16 KB page aligned | `zipalign -c -P 16 4` in CI |

### Permissions

The APK's permission set (after merging every library manifest) must match this reviewed list.
`scripts/ci/apk_audit.py` fails on any other permission, so a library that adds one cannot slip in.

| Permission | Why |
| --- | --- |
| `INTERNET` | Google Calendar and Tasks sync |
| `ACCESS_NETWORK_STATE` | Sync waits for a connection (WorkManager constraint) |
| `POST_NOTIFICATIONS` | Reminders (asked at runtime on Android 13+) |
| `RECEIVE_BOOT_COMPLETED` | Re-plan reminders after a reboot |
| `SCHEDULE_EXACT_ALARM` | Reminders on time; falls back to inexact alarms when not granted |
| `WAKE_LOCK` | Added by WorkManager while a worker runs |
| `FOREGROUND_SERVICE` | Added by WorkManager's manifest. The app starts no foreground service |
| `app.daysemble.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | The app's own signature permission, generated by androidx core for non-exported dynamic receivers |

## CI security controls

| Control | Tool | Blocks |
| --- | --- | --- |
| Secrets in commits | gitleaks 8.30.1 (pull request commits; full history on main and weekly) | any finding |
| Code | CodeQL `security-extended`, java-kotlin | security severity ≥ 7.0 |
| Shipped dependencies | CycloneDX SBOM of `releaseRuntimeClasspath` + OSV-Scanner 2.7.0 | CVSS ≥ 7.0 (pull requests: only dependencies they add or change) |
| Licences | `scripts/ci/deps_check.py` | a licence that is not allowed or reviewed |
| Android lint | security checks promoted to errors | any error |
| APK contents | `scripts/ci/apk_audit.py` | see [CI_CD.md](CI_CD.md#what-each-check-blocks-on) |
| Workflows | actionlint 1.7.12, zizmor 1.31.1 | actionlint errors; zizmor medium and above |
| Build tooling | Gradle wrapper JAR validation; `distributionSha256Sum` pins the Gradle distribution | mismatch |
| Supply chain | Actions pinned to commit SHAs (also required by the repository's Actions setting); tools checked against pinned SHA-256; Dependabot with a 7-day cooldown | unpinned action, checksum mismatch |

Build-tool dependencies (the Android Gradle plugin, lint, KSP and their transitive libraries) do not
ship in the APK. OSV here scans only what ships; build tooling is covered by Dependabot alerts on the
dependency graph and the patched floors in `gradle/libs.versions.toml`.

### Workflow hardening

- Every workflow defaults to `permissions: contents: read`; jobs add only what they use
  (`security-events: write` for CodeQL uploads, `actions: read` to look up CI runs, `contents: write`
  only in the release `publish` job, `id-token`/`attestations: write` only in the attestation job).
- `actions/checkout` runs with `persist-credentials: false` everywhere.
- No `pull_request_target` and no `workflow_run` triggers. Pull requests from forks run with a
  read-only token and no secrets.
- Values from events (branch names, titles) never appear inside `run:` scripts; they are passed
  through `env:`.
- Secrets are referenced only in jobs that declare `environment: release`.
- The release build uses no cache.

### Licence policy

Allowed: Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, ISC, EPL-1.0, EPL-2.0, MPL-2.0, CC0-1.0,

## Reviewed exceptions

Each exception names the finding, why it is accepted, and what compensates. Review them when the
related code changes.

| Finding | Where | Decision |
| --- | --- | --- |
| CodeQL `java/android/backup-enabled` (7.5) | `AndroidManifest.xml` `allowBackup="true"` | Excluded in `.github/codeql/codeql-config.yml`. Backups are intended (settings survive a phone change) and are limited to the settings file, which holds no personal content or tokens. The APK audit fails if backups are enabled without both rule files. |
| Licence "Android Software Development Kit License" (no SPDX id) | `com.google.android.gms` (Play services auth and its base libraries, for Google sign-in; 7 components) | Allowed for `com.google.android.gms` and `com.google.firebase` only (`REVIEWED_NAMED` in `deps_check.py`; no Firebase library ships today). The licence permits distributing the libraries inside an Android app. |
| detekt findings in `config/detekt/baseline.xml` (370) | existing code | Existing style and complexity findings, also reported by Codacy. Only new findings fail CI. Shrink the baseline when touching the code. |
| `FOREGROUND_SERVICE` permission | from WorkManager's manifest | Unused by the app. Can be removed with `tools:node="remove"` once verified that no worker uses `setForeground` (roadmap P3). |

## GitHub settings

These protections are settings, not files, and need to be switched on by the repository admin
(under **Settings**):

1. **Code security → Dependency graph, Dependabot alerts, Dependabot security updates:** enable.
2. **Code security → Secret scanning and push protection:** enable if offered for this repository
   (public repositories, or private ones with GitHub Secret Protection). gitleaks in CI covers
   commits either way; push protection additionally stops a secret before it reaches GitHub.
3. **Code security → Private vulnerability reporting:** enable (the security policy points to it).
4. **Code scanning:** on a public repository, or a private one with GitHub Code Security, set the
   repository variable `CODE_SCANNING_UPLOAD` to `true` (Settings → Secrets and variables → Actions →
   Variables) so CodeQL results also appear in the Security tab. Leave "default setup" off: this
   repository uses the advanced setup in `codeql.yml`, and the two conflict.
5. **Dependency review:** where GitHub's dependency review is available, set the variable
   `DEPENDENCY_REVIEW_ENABLED` to `true` to also run `actions/dependency-review-action`.
6. **Actions → General:** keep "Require actions to be pinned to a full-length commit SHA" on, workflow
   permissions "Read repository contents", and "Allow GitHub Actions to create and approve pull
   requests" off. For a public repository, require approval for fork pull request workflows from all
   external contributors.
7. **Branch protection** for `main`: see [RELEASE.md](RELEASE.md#repository-settings).

## If a secret leaks

1. Revoke or rotate the credential first (deleting the commit does not make it safe).
2. Remove it from history only after rotating, and tell anyone who has cloned the repository.
3. For the release signing key: a leaked key cannot be revoked for already installed apps. Without
   Play App Signing, a new key means existing users must uninstall and reinstall. Keep the keystore
   and its passwords outside the repository, with an offline backup.

## Privacy assessment

What the app does with personal data, as built today. This is a technical description, not a legal
compliance statement: GDPR, India's DPDP Act, Google's API user-data policy and Play's data safety
form need their own review by the maintainer (see below).

| Data | Where it is kept | Leaves the device |
| --- | --- | --- |
| Events, tasks, reminders, sleep logs, schedule | Room database on the device | Only events and tasks in Google calendars and lists, to Google, when an account is connected |
| Settings (theme, logo, schedule preferences) | Settings DataStore | Android backup (Google account backup or device transfer), if the user has it on |
| Google account email, sync switches | Account DataStore | No (not backed up) |
| OAuth access tokens | Memory only | Sent to Google APIs only |

- No analytics, crash reporting, advertising SDKs or Daysemble server. No third-party SDK other than
  Google sign-in (Play services auth).
- OAuth scopes are `auth/calendar` and `auth/tasks` (read and write). These are broad; a narrower set
  (`calendar.events` plus `calendar.calendarlist.readonly`) may be enough and is worth evaluating
  (roadmap P3).
- Disconnecting the account stops sync; the local data stays until the user deletes it or the app.

Needs a manual review by the maintainer before a public release:

- A privacy policy (required for Google OAuth verification of the Calendar and Tasks scopes, and for
  Play). Google's restricted/sensitive scope verification for these scopes.
- Play Console data safety form, if published on Play.
- Whether GDPR or the DPDP Act applies to how the app is distributed, and what that requires.
